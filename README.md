# go-shortener-service

[![CI](https://github.com/D0CCi/go-shortener-service/actions/workflows/ci.yml/badge.svg)](https://github.com/D0CCi/go-shortener-service/actions/workflows/ci.yml)

Сервис сокращения ссылок на Go: принимает оригинальный URL и выдаёт короткий код из 10 символов, по коду возвращает оригинальный URL.

## Запуск

С PostgreSQL (сервис и база в Docker):

```bash
docker compose up -d --build
curl -X POST localhost:8080/ -d '{"url":"https://example.com/very/long"}'
curl localhost:8080/<code>
docker compose down        # данные сохраняются в volume; down -v — удалить и их
```

С хранилищем в памяти:

```bash
docker build -t go-shortener-service .
docker run --rm -p 8080:8080 go-shortener-service              # -storage=memory по умолчанию
```

Без Docker: `go run ./cmd/shortener` (память) или `DATABASE_URL=postgres://... go run ./cmd/shortener -storage=postgres`.

| флаг / переменная | по умолчанию | |
|---|---|---|
| `-storage` | `memory` | `memory` или `postgres` |
| `-addr` | `:8080` | адрес, который слушает сервер |
| `-base-url` | `http://localhost:8080` | префикс коротких ссылок в ответах |
| `DATABASE_URL` | — | строка подключения, обязательна для `postgres` |

## API

| метод | путь | тело запроса | ответ |
|---|---|---|---|
| `POST` | `/` | `{"url": "https://example.com/very/long"}` | `201` — ссылка создана, `200` — уже существовала |
| `GET` | `/{code}` | — | `200` — ссылка найдена |

Оба метода возвращают одно и то же представление ресурса:

```json
{"url": "https://example.com/very/long", "short_url": "http://localhost:8080/aB3_xYz9Q1"}
```

Ошибки — всегда JSON вида `{"error": "..."}`:

| ситуация | код |
|---|---|
| битый JSON, пустой или невалидный URL | `400` |
| код неверной длины или с недопустимыми символами (отсекается до обращения к хранилищу) | `400` |
| код корректный, но не найден | `404` |
| неизвестный путь | `404` |
| неподдерживаемый метод (с заголовком `Allow`) | `405` |
| внутренняя ошибка (детали только в логе, клиенту не раскрываются) | `500` |

## Архитектура

```
cmd/shortener/          точка входа: конфиг, сборка зависимостей, запуск сервера
internal/
  shortcode/            генерация и проверка 10-символьных кодов
  shortener/            бизнес-логика: Shorten, Resolve, повторы при коллизии
  storage/              общие ошибки хранилищ (ErrNotFound, ErrCodeExists)
  storage/memory/       хранилище в памяти
  storage/postgres/     хранилище в PostgreSQL
  httpapi/              HTTP-хендлеры
```

- Зависимости направлены в одну сторону: `httpapi → shortener → интерфейс Storage`. Бизнес-логика не знает, какое хранилище используется, поэтому его можно выбирать флагом при запуске.
- Интерфейс `Storage` объявлен на стороне потребителя (`shortener`), реализации удовлетворяют ему неявно.
- Ошибки объявляет тот, кто их производит: контракт хранилищ — в `storage`, правила сервиса — в `shortener`.
- Нижние пакеты не знают о верхних: `shortcode.Valid` возвращает `bool`, а что это значит для бизнеса (`ErrInvalidCode`), решает сервис.

## Принятые решения

### Генерация кода

Код — 10 случайных символов из алфавита `[a-zA-Z0-9_]` (63 символа), источник случайности — `crypto/rand`.

- **Почему случайная строка.** Рассматривались три подхода:
  - *случайная строка* — выбрана: проста, непредсказуема, легко объясняется;
  - *обрезанный хеш от URL* — при коллизии двух разных URL перегенерировать нечего (хеш детерминирован), к тому же по URL можно вычислить код и узнать, сокращал ли его кто-то;
  - *счётчик + base63* — коллизий нет по построению, но коды идут подряд: можно перебрать все ссылки сервиса и оценить объём бизнеса; нужен общий счётчик между инстансами.
- **Почему `crypto/rand`, а не `math/rand`.** Выход `math/rand` предсказуем — по нескольким кодам можно угадать следующие.
- **Без modulo bias.** `256 % 63 = 4`, поэтому наивный `b % 63` делает первые 4 символа алфавита на 25% вероятнее. Байты `>= 252` (порог вычисляется как `256 - 256 % len(alphabet)`) отбрасываются — rejection sampling, тот же подход, что в `crypto/rand.Int`.
- **Цикл без лимита.** Пачка из 16 байт целиком бракуется с вероятностью `(4/256)^16 ≈ 10⁻²⁹`, поэтому цикл практически всегда завершается за одну итерацию.
- **Вероятность коллизии.** Всего `63^10 ≈ 9.8·10¹⁷` кодов. При миллиарде сохранённых ссылок новый код совпадёт с существующим с вероятностью `≈ 10⁻⁹`.
- **Коллизии обрабатывает не генератор, а хранилище** (уникальность кода гарантирует оно), а сервис при коллизии генерирует новый код — до `maxAttempts = 5` попыток.

### Хранилище в памяти

- Две мапы: `code → url` (для GET) и `url → code` (чтобы на один URL была одна ссылка). Обе операции — O(1).
- Один `sync.RWMutex` на обе мапы: они должны меняться вместе, иначе другая горутина увидит «половину» записи.
- `sync.Map` не подходит: он защищает одну мапу, а нужна атомарность изменения двух.
- `SaveURL` — одна атомарная операция под одним локом: «URL уже есть → вернуть его код; код занят → `ErrCodeExists`; иначе записать». Разнесение проверки и записи на два вызова дало бы гонку (два кода на один URL или перезапись чужой ссылки).
- Под локом — только операции с мапами; код генерируется до захвата лока.
- Данные не переживают перезапуск — это осознанное свойство режима (разработка, тесты). Для продакшена — PostgreSQL.

### Хранилище PostgreSQL (в работе)

- Драйвер `pgx/v5` с пулом соединений `pgxpool` — запросы разных пользователей не ждут друг друга в очереди к одному соединению.
- Таблица `links`: `code` — первичный ключ; уникальность URL — по колонке `url_hash = sha256(url)` с `UNIQUE`. Индекс B-tree не принимает записи длиннее ~2.7 КБ, а URL может быть до 4096 символов — хеш всегда 32 байта (подход Shlink). Проверено: `UNIQUE` по самому `url` на случайной строке из 4096 символов падает с `index row size exceeds maximum`, и Postgres сам советует индекс по хешу.
- Хеш считает Go (`sha256.Sum256`), а не база. Вычисляемая колонка `GENERATED AS (sha256(convert_to(url, 'UTF8')))` не создаётся: `convert_to` помечена в Postgres как `STABLE`, а в выражении колонки допустимы только `IMMUTABLE` функции. Приведение `url::bytea` не подходит — оно разбирает экранирование (`\x41` → `A`), и разные URL получили бы один хеш.
- `SaveURL` — `INSERT ... ON CONFLICT (url_hash) DO NOTHING RETURNING code`: атомарность обеспечивает база, как мьютекс в памяти. Нет строки — URL уже есть, берём его код; нарушение первичного ключа — `ErrCodeExists`.
- Строка подключения — из переменной окружения `DATABASE_URL`, а не флагом: в ней пароль, а аргументы процесса видны всем (`ps`).
- Схема создаётся при старте из вшитого в бинарник SQL (`CREATE TABLE IF NOT EXISTS`). Для продакшена — инструмент миграций (`goose`).

### Сервер

- Таймауты `http.Server`: заголовки — 5 с, весь запрос и ответ — по 10 с, простой keep-alive — 60 с. Без них медленные клиенты держат соединения и горутины бесконечно (slowloris).
- Тело запроса ограничено 8 КБ (`http.MaxBytesReader`).
- Корректная остановка: по `SIGINT`/`SIGTERM` сервер перестаёт принимать новые соединения и дожидается текущих запросов до 5 с — меньше, чем `docker stop` ждёт перед `SIGKILL` (10 с).
- Логи — `log/slog`, структурированные. Пишутся только ошибки 500 (метод, путь, причина); 400/404 — ошибки клиента, иначе любой сканер засыпал бы лог.

### Docker

- Двухстадийная сборка: в первой стадии Go собирает статический бинарник (`CGO_ENABLED=0`), во вторую попадает только он. Итоговый образ — ~22 МБ вместо ~300 МБ с компилятором.
- Базовый образ `distroless/static:nonroot`: нет shell и пакетного менеджера (меньше поверхность атаки), процесс работает не от root.
- `go.mod` и `go.sum` копируются до исходников — слой с зависимостями пересобирается только при их изменении.
- Версия Go закреплена точно (`golang:1.27.1-alpine`), чтобы сборка не зависела от того, что лежит в локальном кеше.
- В compose сервис ждёт `healthcheck` базы (`pg_isready`), а не просто запуска контейнера; данные PostgreSQL — в volume. Порт базы наружу не открыт.

### Неоднозначности ТЗ

ТЗ не уточняет, что считать «одним оригинальным URL» и какие ссылки принимать; по ответу команды такие моменты остаются на выбор исполнителя. За основу взято поведение Яндекс Кликера (`clck.ru`) — проверено ~70 запросами к его API:

- символы табуляции и перевода строки внутри ссылки удаляются, пробелы по краям обрезаются;
- длина — не больше 4096 символов;
- URL без схемы (`example.com`) дополняется `http://`. Схемой считается слово из букв, цифр, `+`, `-` перед первым `:` (как в Kutt): поэтому `example.com:8080` — это хост с портом, а `localhost:8080` и `mailto:a@b.c` — схема без хоста, отклоняются (Кликер ведёт себя так же);
- схема любая (`https`, `ftp`, `ssh`, `wss`...), но после неё обязателен хост с точкой: `localhost`, `tg://resolve`, `chrome://settings`, IPv6 отклоняются, IPv4 принимается; `mailto:`, `magnet:`, `about:` отклоняются — у них нет хоста;
- ссылки с логином (`https://user@host`) и `javascript://example.com/...` принимаются, как в Кликере. Сервис не делает редирект и не рендерит HTML, а браузеры не переходят на `javascript:` по редиректу; клиент, который вставляет ссылку в страницу, обязан её экранировать;
- порт — число от 1 до 65535; пустые метки в домене (`a..b.com`) запрещены;
- кириллический (и любой не-ASCII) домен переводится в Punycode: `пример.рф` и `ПРИМЕР.РФ` → `xn--e1afmkfd.xn--p1ai`; не-ASCII символы в пути кодируются (`%D0%BF...`);
- больше ничего не нормализуется: `EXAMPLE.com`, `:443`, `https://a.ru` и `https://a.ru/`, порядок параметров — разные ссылки. Сохраняется и в ответах `POST` и `GET` возвращается результат этих шагов — клиент сразу видит, что именно сохранено (`пример.рф` → `http://xn--e1afmkfd.xn--p1ai`);
- `GET /{code}` возвращает URL в JSON, а не делает редирект: ТЗ требует «возвращать оригинальный URL».

Ошибка всегда одна — `ErrInvalidURL` (HTTP 400), к ней добавляется причина: `empty`, `longer than 4096 characters`, `malformed`, `missing host`, `invalid port`, `invalid domain`, `domain must contain a dot`. Обработчику нужна категория (`errors.Is`), человеку — причина в тексте.

Отличия от Кликера — только там, где он выдаёт нерабочую ссылку или падает:

| вход | Кликер | здесь |
|---|---|---|
| `example.com:8080/a` | сохраняет без схемы — ссылка не откроется | `http://example.com:8080/a` |
| `https://exa mple.com/` | сохраняет `exa+mple.com` — такого домена нет | 400 |
| `https://a..b.com/` | 500 Internal Server Error | 400 |
| `HTTP://example.com` | хранит как есть | схема в нижнем регистре (регистр схемы не значим по RFC 3986) |

Риск фишинга по ссылкам с логином (`https://bank.ru@evil.com` ведёт на `evil.com`) Кликер закрывает проверкой при переходе (Safe Browsing, `sba.yandex.ru`) — см. «Что можно добавить для продакшена».

Ограничение B-tree индекса PostgreSQL (~2.7 КБ на запись) меньше лимита длины, поэтому уникальность URL обеспечивается индексом по `sha256(url)`, как в Shlink.

**Почему своя проверка, а не библиотека.** Кандидаты прогнаны на ~30 граничных случаях:

- `go-playground/validator` (`http_url`), `govalidator.IsURL` — обе пропускают `https://bank.ru@evil.com`; `govalidator` отклоняет `HTTPS://EXAMPLE.com` и принимает `mailto:`, `http_url` не принимает URL без схемы;
- `purell`, `urlx`, `nlnwa/whatwg-url` — нормализаторы, ничего не проверяют; `urlx` к тому же превращает `mailto:a@b.c` в `http://mailto:a@b.c`.

Открытые сокращатели (Kutt, Dub, YOURLS, Shlink) устроены так же: разбор URL + собственные правила. Поэтому — `net/url` для разбора, `golang.org/x/net/idna` (пакет команды Go) для Punycode и несколько своих правил.

## Долгая работа и нагрузка

- **Память.** In-memory хранилище растёт без ограничений — удаления нет, потому что короткие ссылки должны жить вечно. Порядок: ~200–300 байт на запись, ~300 МБ на миллион ссылок.
- **Поиск URL в PostgreSQL.** На таблице из 1 млн ссылок (`EXPLAIN ANALYZE`, PostgreSQL 18):

  | условие | план | прочитано страниц | время |
  |---|---|---|---|
  | `WHERE url = $1` (индекса нет) | `Parallel Seq Scan`, 1 млн строк | 13 235 | 60.9 мс |
  | `WHERE url_hash = $1` (уникальный индекс) | `Index Scan` | 4 | 0.11 мс |

  Поиск по хешу быстрее в ~500 раз и не зависит от размера таблицы.
- **Конкурентность.** Хранилище в памяти потокобезопасно; проверено конкурентным тестом (100 горутин сохраняют один URL — все получают один код) и `go test -race`.

## Что можно добавить для продакшена

Сознательно не реализовано, чтобы не усложнять решение сверх ТЗ:

- проверка ссылок на фишинг и вредоносность (Google Safe Browsing / Яндекс Safe Browsing API), как делает Кликер;
- rate limiting (на сервисе или на reverse proxy) — защита от злоупотреблений и перебора кодов;
- редирект `GET /{code}` → `302 Location` вместо JSON (ТЗ требует «возвращать оригинальный URL»);
- кеш горячих ссылок перед PostgreSQL;
- метрики (Prometheus) и трейсинг;
- TTL ссылок и удаление.

## Тесты

```bash
go test ./...          # нужен запущенный Docker: тесты PostgreSQL поднимают свою базу
go test -short ./...   # без Docker, тесты PostgreSQL пропускаются
```

- Оба хранилища проходят один и тот же набор тестов (`internal/storage/storagetest`): новая ссылка, повторный URL, занятый код, поиск, URL максимальной длины, 100 одновременных сохранений одного URL. Так гарантируется, что они взаимозаменяемы.
- PostgreSQL в тестах — настоящий, в контейнере (`testcontainers-go`), а не мок: проверяются реальные SQL, ограничения и коды ошибок. Контейнер один на пакет, таблица очищается перед каждым тестом.

CI (GitHub Actions) на каждый push запускает `golangci-lint`, `go test -race` вместе с тестами PostgreSQL и сборку Docker-образа.

`-race` требует cgo. На Windows без gcc можно запустить в контейнере:

```bash
docker run --rm -v ${PWD}:/app -w /app golang:1.27.1 go test -race -short ./...
```
