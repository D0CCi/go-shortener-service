# go-shortener-service

Сервис сокращения ссылок на Go: принимает оригинальный URL и выдаёт короткий код из 10 символов, по коду возвращает оригинальный URL.

> Статус: в разработке.

## API

| метод | путь | тело запроса | ответ |
|---|---|---|---|
| `POST` | `/` | `{"url": "https://example.com/very/long"}` | `201` — ссылка создана, `200` — уже существовала |
| `GET` | `/{code}` | — | `200` — ссылка найдена |

Оба метода возвращают одно и то же представление ресурса:

```json
{"url": "https://example.com/very/long", "short_url": "http://localhost:8080/aB3_xYz9Q1"}
```

Ошибки — всегда JSON вида `{"error": "..."}`:

| ситуация | код |
|---|---|
| битый JSON, пустой или невалидный URL | `400` |
| код неверной длины или с недопустимыми символами (отсекается до обращения к хранилищу) | `400` |
| код корректный, но не найден | `404` |
| неподдерживаемый метод | `405` |
| внутренняя ошибка (детали только в логе, клиенту не раскрываются) | `500` |

## Архитектура

```
cmd/shortener/          точка входа: конфиг, сборка зависимостей, запуск сервера
internal/
  shortcode/            генерация и проверка 10-символьных кодов
  shortener/            бизнес-логика: Shorten, Resolve, повторы при коллизии
  storage/              общие ошибки хранилищ (ErrNotFound, ErrCodeExists)
  storage/memory/       хранилище в памяти
  storage/postgres/     хранилище в PostgreSQL
  httpapi/              HTTP-хендлеры
```

- Зависимости направлены в одну сторону: `httpapi → shortener → интерфейс Storage`. Бизнес-логика не знает, какое хранилище используется, поэтому его можно выбирать флагом при запуске.
- Интерфейс `Storage` объявлен на стороне потребителя (`shortener`), реализации удовлетворяют ему неявно.
- Ошибки объявляет тот, кто их производит: контракт хранилищ — в `storage`, правила сервиса — в `shortener`.
- Нижние пакеты не знают о верхних: `shortcode.Valid` возвращает `bool`, а что это значит для бизнеса (`ErrInvalidCode`), решает сервис.

## Принятые решения

### Генерация кода

Код — 10 случайных символов из алфавита `[a-zA-Z0-9_]` (63 символа), источник случайности — `crypto/rand`.

- **Почему случайная строка.** Рассматривались три подхода:
  - *случайная строка* — выбрана: проста, непредсказуема, легко объясняется;
  - *обрезанный хеш от URL* — при коллизии двух разных URL перегенерировать нечего (хеш детерминирован), к тому же по URL можно вычислить код и узнать, сокращал ли его кто-то;
  - *счётчик + base63* — коллизий нет по построению, но коды идут подряд: можно перебрать все ссылки сервиса и оценить объём бизнеса; нужен общий счётчик между инстансами.
- **Почему `crypto/rand`, а не `math/rand`.** Выход `math/rand` предсказуем — по нескольким кодам можно угадать следующие.
- **Без modulo bias.** `256 % 63 = 4`, поэтому наивный `b % 63` делает первые 4 символа алфавита на 25% вероятнее. Байты `>= 252` (порог вычисляется как `256 - 256 % len(alphabet)`) отбрасываются — rejection sampling, тот же подход, что в `crypto/rand.Int`.
- **Цикл без лимита.** Пачка из 16 байт целиком бракуется с вероятностью `(4/256)^16 ≈ 10⁻²⁹`, поэтому цикл практически всегда завершается за одну итерацию.
- **Вероятность коллизии.** Всего `63^10 ≈ 9.8·10¹⁷` кодов. При миллиарде сохранённых ссылок новый код совпадёт с существующим с вероятностью `≈ 10⁻⁹`.
- **Коллизии обрабатывает не генератор, а хранилище** (уникальность кода гарантирует оно), а сервис при коллизии генерирует новый код — до `maxAttempts = 5` попыток.

### Хранилище в памяти

- Две мапы: `code → url` (для GET) и `url → code` (чтобы на один URL была одна ссылка). Обе операции — O(1).
- Один `sync.RWMutex` на обе мапы: они должны меняться вместе, иначе другая горутина увидит «половину» записи.
- `sync.Map` не подходит: он защищает одну мапу, а нужна атомарность изменения двух.
- `SaveURL` — одна атомарная операция под одним локом: «URL уже есть → вернуть его код; код занят → `ErrCodeExists`; иначе записать». Разнесение проверки и записи на два вызова дало бы гонку (два кода на один URL или перезапись чужой ссылки).
- Под локом — только операции с мапами; код генерируется до захвата лока.
- Данные не переживают перезапуск — это осознанное свойство режима (разработка, тесты). Для продакшена — PostgreSQL.

### Неоднозначности ТЗ

ТЗ не уточняет, что считать «одним оригинальным URL»; по ответу команды такие моменты остаются на выбор исполнителя. Решение:

- URL без схемы (`example.com`) принимается и дополняется `http://`: такая ссылка откроется всегда — сайт на https сам перенаправит, а сайт только на http не сломается;
- приводить URL к канонической форме только преобразованиями, которые RFC 3986 (раздел 6) называет безопасными: регистр схемы и хоста, порт по умолчанию, пустой путь → `/`, кириллические домены → Punycode;
- `http` и `https` — разные ресурсы, не объединяются; путь, параметры и якорь не трогаются;
- принимаются только схемы `http`/`https` (`javascript:`, `data:` и т. п. — риск фишинга под доменом сервиса); ссылки с логином (`https://bank.ru@evil.com`) отклоняются;
- длина URL ограничена 2048 символами;
- в хранилище попадает и по `GET` возвращается каноническая форма — это тот же ресурс, а ответ не зависит от того, кто прислал ссылку первым;
- `GET /{code}` возвращает URL в JSON, а не делает редирект: ТЗ требует «возвращать оригинальный URL».

## Долгая работа и нагрузка

- **Память.** In-memory хранилище растёт без ограничений — удаления нет, потому что короткие ссылки должны жить вечно. Порядок: ~200–300 байт на запись, ~300 МБ на миллион ссылок.
- **Конкурентность.** Хранилище в памяти потокобезопасно; проверено конкурентным тестом (100 горутин сохраняют один URL — все получают один код) и `go test -race`.

## Что можно добавить для продакшена

Сознательно не реализовано, чтобы не усложнять решение сверх ТЗ:

- rate limiting (на сервисе или на reverse proxy) — защита от злоупотреблений и перебора кодов;
- редирект `GET /{code}` → `302 Location` вместо JSON (ТЗ требует «возвращать оригинальный URL»);
- кеш горячих ссылок перед PostgreSQL;
- метрики (Prometheus) и трейсинг;
- TTL ссылок и удаление.
